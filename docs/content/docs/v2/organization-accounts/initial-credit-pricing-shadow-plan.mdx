# 首版积分价格与 Shadow 试算方案

本文为 FP-ORG-006 的首版商业参数建议，用于在开发和测试环境先执行 Shadow 计费。数值是内部积分种子价，不代表供应商公开报价，也不直接承诺人民币、日元或美元价值；Shadow 结束后应依据真实流量、供应商账单和目标毛利发布新的不可变价格版本。

## 1. 当前基线

当前 seed 配置可初始化以下 Azure OpenAI Deployment：

| 能力 | 当前 Deployment | 当前可计量字段 |
| --- | --- | --- |
| 文本 | `gpt-5.6-sol` | `inputTokens`、`cachedTokens`、`outputTokens`、`reasoningTokens`、`totalTokens` |
| 图片 | `gpt-image-2` | `images`、`imageSize`、`imageQuality` |
| 视频 | `sora-2` | `videos`、`videoSeconds`、`videoResolution` |
| 音频 | 当前 seed 未配置 | `audioCharacters`、`audioSeconds` |

模型最终仍以管理后台数据库中的启用模型为准，环境变量只负责补充缺失的初始模型。任一模型进入 Shadow 前，都必须存在唯一生效的价格版本；未配置的音频模型不应为了凑齐矩阵而虚构可用模型。

现有 `usageSource` 含义保持不变：

- `provider`：供应商响应返回了可用 Token。
- `estimated`：文本供应商未返回 Token，由后台 tokenizer 或字符数估算。
- `none`：没有 Token；媒体任务仍可通过 `mediaUnits` 计价，失败、取消或不可计量请求可能为零。

## 2. 建议的积分最小单位

建议数据库继续只保存整数最小单位 `unit`，界面显示：

```text
1 积分 = 1,000 units
1 unit = 0.001 积分
```

金额、余额、预占、结算、退款和上限都以 `unit` 运算，界面最多显示 3 位小数。该比例可以覆盖千 Token、小批量图片和短音视频的细粒度价格，同时避免浮点余额。所有公式先在整数分子上计算，最后对一次任务总价执行一次 `ceil`，不要对每个 Token 或每个价格项分别进位。

本文后续矩阵均以 `units` 表示；括号内为界面积分。

## 3. 首版建议价格矩阵

### 3.1 文本：`gpt-5.6-sol`

| 计量项 | 建议价 |
| --- | ---: |
| 非缓存输入 Token | 10 units / 1,000 Token |
| 缓存输入 Token | 2 units / 1,000 Token |
| 可见输出 Token | 40 units / 1,000 Token |
| 推理 Token | 40 units / 1,000 Token |

Token 明细通常存在包含关系。为了避免重复计费，首版公式应使用拆分后的量，而不是把原始总量直接相加：

```text
nonCachedInput = max(0, inputTokens - cachedTokens)
visibleOutput = max(0, outputTokens - reasoningTokens)

units = ceil((nonCachedInput × 10
            + cachedTokens × 2
            + visibleOutput × 40
            + reasoningTokens × 40) / 1,000)
```

如果某供应商明确声明其 `inputTokens` 或 `outputTokens` 不包含对应明细，才允许由该 Provider 适配规则覆盖拆分方式；不得仅根据字段同时非零就额外累加。

预占按模型 `maxOutputTokens` 上限、完整输入和最高可能的输出/推理费率计算。`reasoningEffort` 首版不另设倍率，真实差异已经反映在推理 Token 中。

### 3.2 图片：`gpt-image-2`

单价为每张图片的 units：

| `imageSize` | `low` | `medium` / `auto` | `high` |
| --- | ---: | ---: | ---: |
| `1024x1024` / `auto` | 400（0.400） | 1,000（1.000） | 1,800（1.800） |
| `1536x1024` / `1024x1536` | 600（0.600） | 1,500（1.500） | 2,700（2.700） |

```text
units = images × matrix[normalizedSize][normalizedQuality]
```

`auto` 在首版按 `1024x1024 + medium` 结算，但预占按当前请求可能命中的最高档计算。进入 Hard 前，应把该模型的 `size` 和 `quality` 参数收敛为可枚举值，并用真实响应确认 `auto` 的最终规格；未知尺寸或质量不得静默套用最低价。

### 3.3 视频：`sora-2`

单价为每个实际生成秒的 units：

| `videoResolution` | 建议秒价 |
| --- | ---: |
| `480p` | 180（0.180）/ 秒 |
| `720p` / 缺省 | 300（0.300）/ 秒 |
| `1080p` | 600（0.600）/ 秒 |

```text
units = ceil(videoSeconds) × rate[normalizedResolution]
```

Azure 视频请求会把时长修正到供应商支持的档位，结算必须使用结果中记录的实际 `videoSeconds`，例如请求 6 秒而实际执行 8 秒时按 8 秒结算。当前 `mediaUnits` 没有保存 `generateAudio`、水印或其他模式字段，因此首版不对这些参数另加价，成本缓冲已包含在秒价中；在增加可审计字段前不得仅凭请求参数做额外结算。

当前模型参数同时存在 `size` 和 `resolution`，但用量只保存 `videoResolution`。Shadow 阶段应把缺失、无法从 `size` 归一化或不在矩阵内的值标记为 `pricing_gap`；修正字段口径并重新试算后才能为该模型开启 Hard。

### 3.4 音频：未来语音模型的首版占位规则

当前接口只实现文本转语音，建议首个音频模型按输入字符计价：

| operation | 建议价 | 结算字段 |
| --- | ---: | --- |
| `tts` | 15 units / 100 字符 | `audioCharacters` |

```text
units = ceil(audioCharacters × 15 / 100)
```

`audioSeconds` 保留用于用量展示和供应商账单对账，不与字符数重复收费。只有未来接入按秒收费的语音能力时，才新增独立 operation 和秒价；同一 operation 必须只选择一种结算主单位。音频模型尚未配置，因此该规则不进入首个已发布价格版本。

## 4. 典型请求试算

| 场景 | 用量 | 计算 | 结果 |
| --- | --- | --- | ---: |
| 短文本问答 | 输入 800，缓存 0；输出 300，推理 0 | `ceil((800×10 + 300×40)/1000)` | 20 units（0.020 积分） |
| 带缓存和推理的文本 | 输入 2,400，其中缓存 600；输出 900，其中推理 300 | `ceil((1800×10 + 600×2 + 600×40 + 300×40)/1000)` | 56 units（0.056 积分） |
| 标准图片 | 1 张，`1024x1024`，`medium` | `1×1000` | 1,000 units（1.000 积分） |
| 高清竖图两张 | 2 张，`1024x1536`，`high` | `2×2700` | 5,400 units（5.400 积分） |
| 默认视频 | 6 秒请求被供应商修正为 8 秒，`720p` | `8×300` | 2,400 units（2.400 积分） |
| 1080p 视频 | 12 秒，`1080p` | `12×600` | 7,200 units（7.200 积分） |
| 未来 TTS | 560 字符 | `ceil(560×15/100)` | 84 units（0.084 积分） |

价格预览接口至少内置上表，并为图片、视频自动生成当前 `paramSchema` 全组合。试算输出同时展示原始用量、归一化用量、价格版本、理论 units、界面积分和异常标签。

## 5. `estimated` 与 `provider` 的处理

### 5.1 单次任务结算优先级

1. Token 存在 `provider` 数据时，以供应商数据为权威，保存原字段和价格快照。
2. 文本没有供应商 Token 时，使用现有后台估算并标记 `estimated`；不修改为 `provider`。
3. 媒体没有 Token 不代表免费，按 `mediaUnits` 结算，Token 来源仍可为 `none`。
4. 文本为 `none`，或媒体缺少结算所需主单位时，不猜测用量：释放预占并记录 `usage_missing` / `pricing_gap`，由平台承担未知成本。
5. 失败或取消若已有供应商实际用量则按实际量结算；否则释放全部预占。

### 5.2 首版价格差异

建议 Shadow 和 Soft 阶段对 `estimated` 使用与 `provider` 相同的名义费率，不做折扣，也不把估算值伪装成供应商值。这样最容易观察估算器本身的偏差。无论来源如何，实际结算都不得超过任务预占额。

Hard 阶段不建议用一个全局折扣掩盖误差。按 `provider + model` 分组达到以下门槛后，该模型的 `estimated` 才可按 100% 名义价进入 Hard：

- 至少 200 条可比较成功样本；
- `WAPE = Σ|estimated-provider| / Σprovider ≤ 5%`；
- P95 绝对百分比误差不超过 15%；
- 没有持续单向高估，平均有符号误差绝对值不超过 3%。

未达到门槛时，该模型可以继续 Shadow/Soft，或在 Hard 中只接受返回 provider 用量的请求；不要临时采用 80%、90% 等未经验证的折扣。

### 5.3 可比较样本

当前一条 `ai_usage_records` 只保存一个权威来源。Shadow 分析时，可对 `provider` 文本记录使用同版本 tokenizer 旁路计算 `estimatedComparable`，仅写入 Shadow 试算结果或离线报表，不覆盖 `inputTokens` 等权威字段，也不改变 `usageSource`。比较时固定 `modelId`、Provider、tokenizer 名称/版本和估算方法，禁止跨模型合并后计算一个平均误差。

## 6. Shadow 执行方案

### 阶段 A：发布前构造试算

- 为 `gpt-5.6-sol` 覆盖无缓存、有缓存、无推理、有推理、最大输出预占和一次进位边界。
- 为 `gpt-image-2` 覆盖全部允许的尺寸 × 质量 × 数量组合。
- 为 `sora-2` 覆盖 4/8/12 秒、全部允许分辨率、请求时长被修正和缺失分辨率。
- 音频模型接入后再加入字符数 0/1/99/100/101、长文本和可解析/不可解析时长。
- 同一输入重复试算必须得到完全相同的整数 units；缺字段和未知枚举必须产生异常，不得默认最低价。

### 阶段 B：真实 Shadow 流量

建议至少运行 14 个自然日，并同时满足每个拟开启 Hard 的模型至少 500 条成功任务；低频模型可以延长观察期，不用虚构流量补足。

每天按公司、模型、能力和 `usageSource` 汇总：

- 请求数、成功/失败/取消数；
- 理论预占、理论结算、释放和超预占次数；
- 平均、P50、P95、P99 单请求积分；
- `provider` / `estimated` 数量和占比；
- `pricing_gap`、`usage_missing`、未知参数组合；
- 供应商账单可取得时的 `理论积分 / 供应商成本` 分布。

Shadow 仍完整创建 reservation、settlement 和 release，但账户 `balance_delta`、`reserved_delta` 保持 0，理论值单独保存。价格版本切换只影响新 reservation，在途任务继续使用锁定版本。

### 阶段 C：退出 Shadow 的门槛

一个模型只有同时满足以下条件才进入 Soft：

- 构造矩阵 100% 通过，所有允许参数组合均有价格；
- `pricing_gap = 0`，`PRICING_RESERVATION_MISMATCH = 0`；
- 预占覆盖率 100%，且 P95 的“预占 / 实际结算”不高于 2 倍；
- `estimated` 达到上一节误差门槛，或明确限制为 provider 用量才可 Hard；
- 理论积分与供应商账单的成本倍率落在业务确认区间；
- 连续 7 天账户、预占、结算和流水核对无差异。

Soft 至少观察 7 天并确认 80%/100% 预警不会造成明显误导，再只对测试公司开启 Hard。任一价格缺失、超预占或核对异常都只暂停受影响的 `companyId + modelId`。

## 7. 建议的首版示例额度

为便于 Shadow 报表理解，可以先用以下非销售承诺值：

| 参数 | 建议值 |
| --- | ---: |
| 新建测试公司演示余额 | 100,000 units（100 积分） |
| 测试公司月上限 | 80,000 units（80 积分） |
| 普通测试成员月上限 | 20,000 units（20 积分） |
| 余额/周期预警 | 80% / 100% |

Shadow 模式不实际扣减余额；这些值只用于验证页面展示、理论越限告警和 Soft 行为，不能直接作为正式套餐承诺。

## 8. 需要最终确认的商业参数

进入 Shadow 开发前只需确认以下四项：

1. **显示比例**：是否接受 `1 积分 = 1,000 units`，界面显示 3 位小数。
2. **种子价**：是否接受本文四类能力矩阵作为首版 Shadow 价格；当前实际发布只含 `gpt-5.6-sol`、`gpt-image-2`、`sora-2`。
3. **商业目标**：Shadow 对账时希望理论积分对应的目标成本倍率或毛利区间；未确认前只报告成本倍率，不据此自动改价。
4. **estimated 上线规则**：建议采用“Shadow/Soft 同价；达到误差门槛后 Hard 同价，否则该模型继续 Shadow/Soft 或仅接受 provider 用量”，不采用固定折扣。

以上确认后，初始余额、公司月上限和成员月上限仍可作为运营配置调整，不需要写死进模型价格版本。

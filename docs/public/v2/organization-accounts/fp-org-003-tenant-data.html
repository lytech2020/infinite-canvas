1. 文档信息

状态：确认済。真实存储由独立的 projects、uploads、upload_references、generation_jobs、ai_usage_records 与通用 user_data(user_id,key,value JSONB) KV 组成；素材、工作台历史、插件、提示词源和 Agent 会话均在 user_data 中，不假设存在独立业务表。

2. 功能点输入整理

目的防止公司之间数据泄露，并让公司管理员查看本公司员工业务内容
确认规则归档员工的数据永久保留原公司、原创建人和历史快照
范围外跨公司协作、项目转公司、匿名共享链接

4. 最小修改方针

采用追加式方案 A：不拆 user_data。业务记录同时保留 company_id 和 user_id，前者是租户安全边界，后者是创建人和默认访问范围。公司内容审查按成员和 key 命名空间列出 user_data，只支持单条 blob 查看，不承诺跨 JSON 字段筛选、全局分页或 item 级索引。

9. API 详细设计

方法路径范围
GET/api/v1/company/members/{userId}/content按独立记录类型或 user_data key 列出本公司成员内容
GET/api/v1/company/content/{resourceType}/{resourceId}同一请求内先写审计再返回单条正文；每次读取一条审计
POST/api/v1/company/content/{resourceType}/{resourceId}/media-token审计成功后创建 TTL≤60 秒的一次性兑换 token；只返回 token，不返回对象存储预签名地址
POST/api/v1/company/content/media/{token}/exchange原子消费兑换 token，绑定当前 companyId、sessionId、actor 和 upload，返回 TTL≤60 秒的同源 stream URL；兑换 token 不可再次使用
GET/api/v1/company/content/media/stream/{handle}在流窗口内仅同一会话可多次 Range 读取同一 upload；每次校验绑定与过期时间，窗口到期立即拒绝
GET（変更）/api/v1/generations/{jobId}publicJob 不再返回对象存储预签名 URL；生成文件只返回 uploadId、mimeType、size 和同源 /api/v1/uploads/{uploadId}/content
GET（既存）/api/v1/uploads/{uploadId}/content普通成员本人下载：每次请求重新校验会话、账号状态、companyId、owner userId 和 ready 状态并支持 Range，响应固定 Cache-Control: no-store, private；公司管理员查看他人文件必须走上述强审计 media-token/stream，不得复用本接口绕过审计。公司或账号停用/归档后立即拒绝新下载
既存/projects、/user-data、/uploads、/generations认证上下文自动注入 companyId；成员追加 userId

13. 日志 / 监查 / 运用设计

敏感正文读取与审计写入在同一数据库事务内完成；媒体兑换 token 只在审计成功后签发。兑换接口原子消费 token 并创建同会话短时流窗口；stream handle 在 TTL 内允许浏览器探测、续传和拖动产生的多次 Range 请求，但不能换会话、换公司或换 upload。所有兑换、流和成员生成结果 content 响应均返回 Cache-Control: no-store, private，不得沿用永久媒体代理的 max-age，也不能使用 S3 预签名下载 URL。成员本人查看生成结果必须使用认证同源 content 接口，不下发 bearer 型预签名 URL；停用、归档或公司停用后，后续下载立即按认证优先级拒绝。审计记录查看者、目标成员、资源类型、资源 ID、原因、IP/会话和时间；监控跨公司拒绝、兑换 token 重放和 stream handle 越界次数。

14. 外部接口 / 文件 / 批处理 / 通知

预签名只用于上传，签发前必须同时校验 companyId 与 userId/角色；下载统一经过认证同源代理。生成结果保存时创建持久 uploads 记录并在 job result 中保存 uploadId，publicJob() 不再调用 presignDownload()。清理 Job 只能删除同公司已确认的孤儿对象，不能仅依赖路径前缀。

15. 数据迁移 / 初期数据 / 兼容性

  1. 项目未上线，直接为公司业务记录创建 companyId NOT NULL 与新复合键；users 的条件约束按 FP-ORG-002 的角色 CHECK 执行。
  2. 开发和测试数据由 seed 重建，不编写回填或双前缀兼容。
  3. seed 创建公司后再创建用户、项目和 user_data，保证关联一致。

16. 测试设计观点

  • TEST-FP-ORG-003-001：列表、详情、更新、删除、导出和媒体代理均测试跨公司 ID。
  • TEST-FP-ORG-003-002：公司管理员查看敏感内容成功时一定有审计；审计失败不展示。
  • TEST-FP-ORG-003-003：归档成员历史可由公司管理员查看，归档成员本人不能登录。
  • TEST-FP-ORG-003-004：Agent 消息仍按 threadId、turnId、itemId 去重并增加公司边界；审查粒度为 thread blob。
  • TEST-FP-ORG-003-005：对象存储新前缀、复合归属、兑换 token 只能消费一次；stream handle 允许同会话同 upload 的 Range 探测/续传/拖动，拒绝过期、跨会话、跨公司、换资源，并验证 no-store。
  • TEST-FP-ORG-003-006：生成结果落库后存在 ready persistent uploadId，publicJob 不含对象存储预签名地址；成员通过同源 content 接口完成普通及 Range 下载且响应 no-store，账号/company 停用或归档后旧页面中的 URL 也立即不可下载。

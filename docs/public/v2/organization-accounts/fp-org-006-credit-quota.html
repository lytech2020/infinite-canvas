1. 文档信息

状态：确认済。文本 Token、图片、视频和音频等底层用量统一换算为整数积分。

成员没有可转移的钱包。成员上限只是允许消费公司积分的周期限制；真实余额始终属于公司。

4. 最小修改方针

  1. 现有 ai_usage_records 继续记录原始用量；积分是其上层结算结果。
  2. 模型价格通过追加版本发布，不覆盖历史规则。
  3. credit_accounts 保存事务余额快照，credit_ledger_entries 保存不可变事实。
  4. 生成网关在调用供应商前预占，在现有同进程任务完成处理路径中结算；不新增供应商 webhook，不修改供应商适配器核心协议。
  5. 影子计费、软限制和硬限制分别由系统级功能开关控制；模式在 reserve 时固化。

计价公式

文本积分 = ceil(inputTokens × inputRate
              + cachedTokens × cachedRate
              + outputTokens × outputRate
              + reasoningTokens × reasoningRate)

图片积分 = count × price(model, size, quality)
视频积分 = seconds × price(model, resolution, mode)
音频积分 = seconds/characters × price(model, operation)

实际结算 = max(0, 按价格快照计算的积分)
释放积分 = max(0, 预占积分 - 实际结算)

全链路事务锁序必须统一为 model → company account → member period row。成员锁对象固定为当前 user_id + period_start 的 member_period_limits 行；即使成员“不限额”也保留 credit_limit=NULL 的占位行。事务在取得模型与公司账户锁后执行 INSERT ... ON CONFLICT DO NOTHING 确保占位行存在，再 SELECT ... FOR UPDATE 取得成员锁。改造时删除现有生成服务 user → model 的锁序，不锁 users 行，任何入口都不得保留反向获取路径；任务与预占在同一事务创建，失败时不得留下 active 预占。

预占必须覆盖已校验参数下的最大可计费值。若供应商实际用量异常超过预占，本次最多结算至预占额，记录 PRICING_RESERVATION_MISMATCH；阈值为同一 companyId+modelId 首次发生即暂停该公司该模型的 Hard 新任务并告警，其他公司和模型不受影响，全局暂停只能由平台管理员执行。平台承担差额，不产生负余额或隐藏债务。首期不做自动供应商重试，任何用户重试都生成新的 requestId、jobId 和预占；重复任务完成处理只返回原结算结果。

积分流水类型

typebalance_deltareserved_delta用途
grant正0平台发放
deduct负0平台人工扣减，不能低于已预占
reserve0正创建任务预占
settle负（实际积分）负（全部预占）成功或已确认计费的失败/取消
release0负无费用失败、取消或安全回收
refund正0已结算任务退款
compensate正或负0平台纠错，原因必填

balance_after 和 reserved_after 均表示该事件事务提交后的账户快照。shadow 事件 type 相同但 mode=shadow，delta 均为 0，理论值保存在 reservation/settlement，不改变真实账户。

用量与价格字段契约

能力usage_snapshot 必填字段pricing rule 覆盖字段
textinputTokens, cachedTokens, outputTokens, reasoningTokensinputRate, cachedRate, outputRate, reasoningRate
imageimages, size, qualitysize × quality 的全部 paramSchema 组合
videovideoSeconds, resolution, moderesolution × mode 的全部 paramSchema 组合及秒单价
audioaudioSeconds 或 characters, operationoperation 对应秒价或字符价

实现时为每种 capability 提供 Zod schema。价格发布前必须验证 rule 覆盖该模型 param_schema 的全部允许组合。Hard 周期已用公式写死为：周期窗口内 mode=hard 的 credit_settlements.actual_units 之和 + 当前 mode=hard AND status=active 的 credit_reservations.reserved_units 之和；公司与成员分别按 company_id/user_id 聚合。Shadow/Soft 单独分栏展示，不进入 Hard 额度。聚合优先利用 settlements 的 company_id/user_id + settled_at 与 reservations 的 company_id/user_id + status + created_at 索引，不扫描全量流水。首期统一沿用全局 QUOTA_TIMEZONE，不清零余额、不运行周期重置 Job。

计费模式在 reserve 时写入 credit_reservations.mode，settle、release、refund 和与任务关联的 compensate 一律读取该 reservation 的模式及价格版本；平台模式切换只影响切换后新建的 reservation，在途任务不得读取当前全局模式。无任务的管理员 adjustment 使用独立 Idempotency-Key，并按正式账户调整记录。

13. 日志 / 监查 / 运用设计

  • 余额调整、价格草稿/发布、上限修改、预占、结算、释放、退款、补偿全部留痕。
  • 余额等式：期末 balance = 期初 balance + grant/deduct/settle/refund/compensate 的 balance_delta。
  • 预占等式：期末 reserved = active reservations 汇总 = reserve/settle/release 的 reserved_delta 累计。
  • 任一等式不一致立即停止受影响公司的 Hard 新任务、保留现场并通知平台管理员；只允许追加纠错流水。
  • 超预占暂停由平台管理员在 SCR-FP-ORG-007-005 运维健康页处理。恢复前必须修正或发布价格规则、完成该 companyId+modelId 的账户/预占/结算核对，并通过 Shadow 样例试算；只有平台管理员可执行“恢复 Hard”，必须填写原因并记录暂停事件、证据、操作者和恢复审计。未通过核对不得恢复。
  • 价格发布前使用构造的 capability × 参数组合样例矩阵试算，不依赖尚不存在的历史成本数据。

15. 数据迁移 / 初期数据 / 兼容性

  1. 项目未上线，由 seed 为公司创建 0 余额账户和首个价格版本，不回填旧额度。
  2. V2 直接删除 dailyCallLimit；安全频率限制继续保留。
  3. Shadow 完整走加锁、并发计算、reserve、settle、release 路径，mode=shadow 且账户 delta 为 0；模型全局容量仍可拒绝，公司/成员商业上限只记录不拒绝。
  4. Soft 使用同一路径，公司/成员商业上限显示预警但不拒绝；模型全局容量仍可拒绝。
  5. Hard 才改变真实 balance/reserved，并对公司/成员积分及并发限制执行拒绝。
  6. 任何模式切换只影响新 reservation，在途任务始终以 reservation.mode 完成。
